# Data Lifecycle & Privacy Requirements Checklist: Passwordless Email Login for Enquirers

**Purpose**: Validate that the requirements governing attribution, identity lifetime, retention and discard of codes and sessions, the deliberate absence of attempt history, and what the admin may display are complete, unambiguous, and internally consistent.

**Feature**: [spec.md](../spec.md)
**Depth**: Lightweight sanity pass — highest-risk requirement gaps only

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Requirement Clarity & Measurability

- [ ] CHK001 Is the retention period stated as a requirement with a definite figure, rather than as "long enough to no longer be needed" in the requirement and 30 days only in the success criterion? [Measurability, Spec §FR-059, §SC-015]
- [ ] CHK002 Is "deletes the last such enquiry" defined against a specific operation — hard deletion only, or also archiving, unpublishing, or a status change? [Ambiguity, Spec §FR-058]
- [ ] CHK003 Does the no-attempt-history requirement state whether it constrains application logs and diagnostic output as well as stored records? [Ambiguity, Spec §FR-056, §FR-012]
- [ ] CHK004 Is the maximum acceptable lag between an identity's last enquiry being deleted and its sessions ceasing to work specified? [Measurability, Spec §FR-058]

## Requirement Completeness

- [ ] CHK005 Are requirements defined for whether the automatic discard of codes and finished sessions must run without owner or developer action, and what happens if it does not run? [Gap, Recovery Flow, Spec §FR-059, §FR-060]
- [ ] CHK006 Is it specified whether an address's rate-limit and lockout counters are removed along with its identity, or deliberately outlive it? [Gap, Spec §FR-056, §FR-058]
- [ ] CHK007 Are requirements stated for the fate of an enquiry's stored delivery outcomes and owner reply when that enquiry is deleted? [Coverage, Gap, Spec §FR-058, §FR-060]
- [ ] CHK008 Does the personal-data requirement for the submitter address cover every place it can surface — admin views, owner notifications, and any export — rather than only "not publicly readable"? [Completeness, Spec §FR-002b]
- [ ] CHK009 Is the retention of the sign-in record itself specified for an identity that still has an enquiry but no sessions and no recent activity? [Gap, Spec §FR-034, §FR-058, §FR-059]

## Requirement Consistency

- [ ] CHK010 Is the no-backfill rule stated strongly enough to bind future work, given the owner is the only person who could reasonably want it undone later? [Consistency, Spec §FR-002a, Assumptions]
- [ ] CHK011 Does the requirement that the admin display a block's present state remain consistent with the requirement to store no attempt history — i.e. is the displayed state derivable from counters alone? [Consistency, Spec §FR-055, §FR-056]
- [ ] CHK012 Is the "deletion is the owner's single lever" requirement consistent with the visitor having no deletion route of their own, and is that stated rather than implied? [Consistency, Spec §FR-060, Assumptions]

## Assumptions & Dependencies

- [ ] CHK013 Is the exclusion of a consent or personal-data notice recorded as an explicit, owner-acknowledged out-of-scope decision rather than an omission? [Assumption, Spec Assumptions]
- [ ] CHK014 Is the attribution cut-over documented with its expected duration of visible emptiness, so the empty state's importance is traceable to a stated assumption? [Assumption, Spec §FR-030, Assumptions]
