# Security & Abuse-Resistance Requirements Checklist: Passwordless Email Login for Enquirers

**Purpose**: Validate that the requirements governing enumeration resistance, code handling, rate limiting, session scoping, and the visitor/owner privilege boundary are complete, unambiguous, and objectively verifiable — before implementation begins.
**Created**: 2026-09-08
**Feature**: [spec.md](../spec.md)
**Depth**: Lightweight sanity pass — highest-risk requirement gaps only
**Audience**: Author, self-audit before `/speckit-tasks` and `/speckit-implement`

**Note**: This custom checklist is generated by the `/speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Requirement Clarity & Measurability

- [ ] CHK001 Is "no observable difference in timing" quantified with a tolerance an observer could be tested against, rather than left as an absolute that no implementation can literally meet? [Measurability, Spec §FR-006, §SC-002]
- [ ] CHK002 Are the limit windows specified as fixed or rolling, so that "3 requests per 15 minutes" has exactly one reading? [Ambiguity, Spec §FR-019, §FR-020]
- [ ] CHK003 Is "same origin" defined precisely enough to be verified, including what the system does when the origin cannot be determined at all? [Clarity, Spec §FR-020, Assumptions]
- [ ] CHK004 Is the code's resistance to guessing stated as a requirement relating code length to the attempt limit, rather than only as a 6-digit default in Assumptions? [Clarity, Spec §FR-008, §FR-018]
- [ ] CHK005 Is the maximum acceptable delay between the owner revoking access and every session ceasing to work specified? [Measurability, Spec §FR-035]

## Requirement Completeness

- [ ] CHK006 Do the requirements state whether requesting a new code resets, preserves, or is itself blocked by an in-force incorrect-attempt lockout? [Gap, Spec §FR-009, §FR-018]
- [ ] CHK007 Is the system's behaviour specified for when limit enforcement itself is unavailable — refuse the request or allow it through? [Gap, Recovery Flow, Spec §FR-019, §FR-020]
- [ ] CHK008 Are requirements defined for whether the three limits are enforced independently or can mask one another when more than one applies to the same request? [Gap, Spec §FR-018, §FR-019, §FR-020]
- [ ] CHK009 Is the scope of "any content" in the privilege-boundary requirement enumerated or otherwise made auditable, so the zero-successful-operations criterion has a definite denominator? [Completeness, Spec §FR-037, §SC-008]

## Requirement Consistency

- [ ] CHK010 Does the indistinguishability rule for limit messages explicitly extend to the incorrect-attempt lockout message, or is that message outside its stated scope? [Consistency, Spec §FR-018, §FR-021]
- [ ] CHK011 Is the accepted enumeration signal from delivery failure reconciled against the 100% indistinguishability success criterion, so the two are not read as contradictory? [Conflict, Spec §FR-006, §FR-011, §SC-002, Assumptions]
- [ ] CHK012 Are the requirements for what a refusal may not reveal consistent between the wrong-code case and the wrong-enquiry-identifier case? [Consistency, Spec §FR-017, §FR-029]

## Edge Case & Scenario Coverage

- [ ] CHK013 Are requirements defined for a session presented after its identity has been removed by enquiry deletion, distinct from ordinary expiry? [Coverage, Spec §FR-058, §FR-025]
- [ ] CHK014 Is it specified whether rate-limit and lockout counters keyed to an address survive that address's identity being removed? [Gap, Spec §FR-056, §FR-058]
- [ ] CHK015 Are requirements stated for concurrent use of the same code from two requests arriving at once, given single-use is the property being relied on? [Coverage, Edge Case, Spec §FR-008]
