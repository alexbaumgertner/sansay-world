# Phase 0 Research: SanSay Portfolio Site (Payload CMS)

Each item resolves one unknown from the Technical Context in [plan.md](./plan.md). No
`NEEDS CLARIFICATION` markers remain. Where the owner gave explicit direction, that
direction is recorded as the decision and the research covers *how* to implement it well
and what it costs.

## CMS & application architecture

- **Decision**: Payload CMS 3 mounted inside a single Next.js 15 App Router application,
  using the standard `(frontend)` / `(payload)` route-group split. The public site reads
  content through Payload's **Local API** (`payload.find`, direct DB access in the same
  process), not over HTTP.
- **Rationale**: This is the owner's stated direction and it happens to be the strongest
  fit for the constitution: Principle III ("no-developer content operations") is satisfied
  by a mature, generated admin UI rather than hand-built CRUD screens, and Principle II
  ("extensible by discipline") falls out for free because the enquiry form's discipline
  field is a `relationship` to the disciplines collection — its options *are* the
  collection. The Local API avoids an internal HTTP hop, so public pages render as fast as
  direct queries.
- **Alternatives considered**: A custom admin over Drizzle (the previous iteration of this
  plan) — rejected: every admin screen, upload flow, auth flow, and validation UI would be
  built and maintained by hand for one user. Sanity/Contentful — rejected: content would
  live outside the app's database, and the owner explicitly required enquiries to sit in
  the same database as the content.

## Database

- **Decision**: Neon Postgres via the Vercel Marketplace, using `@payloadcms/db-postgres`.
  Enquiries are a normal collection in this same database.
- **Rationale**: Postgres gives relational integrity for the relationships that matter
  (work sample → discipline, enquiry → discipline) and Payload's Postgres adapter manages
  schema through generated migrations. Vercel Postgres/KV are discontinued, so Marketplace
  Neon is the current managed default; it also offers point-in-time restore, which matters
  because enquiries are irreplaceable business data.
- **Alternatives considered**: MongoDB via `@payloadcms/db-mongodb` — a perfectly common
  Payload choice and slightly less migration ceremony, but rejected because relational
  integrity and PITR-backed durability are worth more here than schema flexibility.
  SQLite — rejected, no persistent local disk on serverless hosting.

## Migrations without the owner running anything

- **Decision**: Payload-generated migration files are committed by the developer; the
  project's `build` script runs `payload migrate` ahead of `next build`, so migrations are
  applied by Vercel during deploy.
- **Rationale**: The owner's constraint is that they must never run a build or a command.
  Binding migrations to the deploy step means schema changes travel with a developer's git
  push and never surface to the owner at all.
- **Alternatives considered**: `push: true` dev-style auto-sync in production — rejected,
  unreviewed schema changes against a production database holding enquiries. Manual
  `payload migrate` runs — rejected, violates the no-CLI constraint the moment the
  developer is unavailable.

## Admin panel & authentication

- **Decision**: Payload's built-in auth on a `users` collection. The first admin user is
  seeded on first run; `create` access is then restricted to authenticated admins, so
  there is no public registration path. Admin UI locale set to Russian.
- **Rationale**: Satisfies FR-030 (single owner login, no self-registration, no roles)
  with framework-native auth — sessions, password hashing, reset flow, and route
  protection all come from Payload rather than being hand-rolled.
- **Alternatives considered**: A custom signed-cookie session (the previous plan's
  approach) — now redundant and rejected: it would sit awkwardly beside Payload's own
  auth, which already guards `/admin` and every collection endpoint.

## Media & preset files

- **Decision**: `@payloadcms/storage-vercel-blob` so uploads land in Vercel Blob rather
  than the (ephemeral) serverless filesystem. Two upload-enabled collections: `media` for
  images, with `imageSizes` generated by `sharp` for card, gallery, and OG use; and
  `preset-files` for downloadable binaries (.zip/.fxp/.wav), no image sizes.
- **Rationale**: Serverless hosting has no durable local disk, so a storage adapter is
  mandatory, not optional. Pre-generated sizes are what keep the mobile LCP target
  reachable — cards never load a full-resolution photograph. The two-collection split is a
  deviation from the literal instruction ("a Payload media collection") and is flagged in
  plan.md's Complexity Tracking: it keeps multi-megabyte preset binaries out of the image
  library the owner browses daily, and collapsing back to one collection is a config-level
  change.
- **Alternatives considered**: S3 via `@payloadcms/storage-s3` — equivalent capability,
  rejected only because it adds an AWS account and IAM setup for no gain on Vercel.
  Storing files in Postgres — rejected outright.

## Enquiry notification delivery

- **Decision**: An `afterChange` hook on the `enquiries` collection, firing only when
  `operation === 'create'`. It attempts email via `@payloadcms/email-resend` (mandatory
  channel) and, when `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are present, a Telegram
  Bot API `sendMessage` call (second channel). Each attempt is independently try/caught,
  the hook never re-throws, and outcomes are written back onto the enquiry document via a
  follow-up update guarded by a `context` flag to prevent hook recursion.
- **Rationale**: This is the owner's stated design and it satisfies Principle VI and
  FR-015/FR-016 precisely: the document is committed before delivery is attempted, so a
  delivery failure can never cancel a stored enquiry, and per-channel outcomes recorded on
  the document are what make the failure visible in the admin. The recursion guard is the
  known Payload gotcha here — an unguarded `payload.update` inside `afterChange` re-enters
  the same hook.
- **Alternatives considered**: Sending from the server action before creating the document
  — rejected, inverts the durability guarantee. A separate queue/cron worker — rejected as
  over-built for a few hundred enquiries a year, though the dispatcher is written behind a
  channel interface so a retry worker could be added later without touching the hook.

## Telegram toggle via environment variable

- **Decision**: Presence and truthiness of `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`
  enables the channel, exactly as directed — no code change required to switch it on.
- **Rationale**: Meets FR-014 ("enable or disable through configuration, without a code
  change") with the simplest possible mechanism and keeps the bot token out of the
  database.
- **Honest caveat**: Vercel applies environment-variable changes at deploy time, so
  flipping this requires editing the variable in the Vercel dashboard and clicking
  "Redeploy" — two clicks, no code, no CLI, but not instant. If the owner would rather
  toggle it themselves from `/admin` with immediate effect, moving the flag to the
  `SiteSettings` global (keeping the token in the env var) is a small, contained change.
  Recorded here so the trade-off is a decision, not an accident.
- **Alternatives considered**: A `SiteSettings` global toggle as the primary mechanism —
  not chosen because the owner specified an environment variable; retained as the
  documented upgrade path.

## Frontend caching & revalidation

- **Decision**: Public pages render from the Local API with tagged caching; `afterChange`
  and `afterDelete` hooks on every content collection call `revalidateTag` /
  `revalidatePath` for the surfaces that collection feeds.
- **Rationale**: This is what makes "the owner presses Save and the site updates" true
  without a rebuild — the critical mechanism behind Principle III and FR-022. Content is
  never baked into a static build that would need regenerating.
- **Alternatives considered**: Fully static export with rebuild-on-publish via a deploy
  hook — rejected: it makes every content edit trigger a build, which is slow, wasteful,
  and exactly the coupling the owner asked to avoid.

## Shows map

- **Decision**: `react-leaflet` with OpenStreetMap raster tiles — no API key, no paid tier.
  The map component is `dynamic(..., { ssr: false })` and wrapped in an error boundary; the
  shows **list renders server-side first and always**, with the map mounted above it as
  progressive enhancement.
- **Rationale**: Meets the "open tiles, no paid key, degrade to the list" requirement
  literally. Because the list is the primary rendering and the map is additive, degradation
  is structural rather than a fallback path that must be tested into existence — if
  Leaflet fails to load, tiles are blocked, or JS is off, the page is still complete.
- **Alternatives considered**: MapLibre GL JS with vector tiles — better looking, but the
  free vector tile providers generally want an API key, which the requirement rules out.
  Mapbox/Google Maps — rejected, paid keys. Note for implementation: OSM's public tile
  service has a usage policy suited to low-traffic sites like this one; if traffic ever
  grows, swapping the tile URL for a self-hosted or sponsored endpoint is a one-line change.

## SEO, social previews, and the hidden Friends page

- **Decision**: The Friends page is an ordinary document in a `pages` collection, as
  directed. Visibility is data: `showInNav`, `includeInSitemap`, and `noindex` boolean
  fields. `src/app/(frontend)/sitemap.ts` filters on `includeInSitemap`; the nav filters on
  `showInNav`; `generateMetadata` emits `robots: { index: false, follow: false }` when
  `noindex` is set; `robots.ts` additionally disallows the Friends path.
- **Rationale**: Keeps hiddenness owner-controlled data rather than a code special case
  (Principle II's spirit), while satisfying FR-024/FR-028 through three independent layers.
  Per-page OG/title/description metadata driven by collection fields covers FR-027.
- **Alternatives considered**: A hardcoded exclusion list in the sitemap route — rejected,
  it would put a page slug in code and break the moment the owner renames it. `next-seo` —
  rejected, Next.js's native Metadata API covers everything needed.

## Accessibility

- **Decision**: Semantic HTML and native form controls throughout; `alt` text is a
  **required** field on image uploads in the `media` collection (enforced by Payload
  validation, so it cannot be skipped at the source); Tailwind tone tokens checked for WCAG
  AA contrast against the dark background; global focus-visible styles; the map is never
  the only route to information the list also carries.
- **Rationale**: Implements FR-031's baseline. Making `alt` required in the CMS is the
  mechanism that makes it stick — a frontend convention would decay as soon as the owner
  uploads in a hurry.
- **Alternatives considered**: axe-core in CI — worth adding at task-planning time, but
  FR-031 explicitly does not require a formal audit, so it is not a blocking gate here.

## Hosting & deployment

- **Decision**: Vercel with Git integration; Neon Postgres and Vercel Blob as managed
  dependencies; deploys triggered by developer pushes; content changes require no deploy
  at all; migrations applied automatically during deploy.
- **Rationale**: The owner's operating loop is: open `/admin`, edit, Save, done. No build,
  no CLI, no deploy button in the normal content path. Payload 3 runs on Vercel's Node
  runtime (needs `sharp` and Node APIs, so Fluid Compute/Node — not Edge). Functions
  serving the admin and uploads should be given generous memory for image processing.
- **Alternatives considered**: **Payload Cloud** — genuinely attractive (managed Postgres,
  storage, and email bundled, purpose-built for Payload) and the right answer if the owner
  ever wants a single vendor and no Vercel account; rejected here only because this project
  is already on Vercel infrastructure. **Railway/Render** — a long-running Node server
  avoids all serverless caveats (cold starts, upload limits) and is the safer choice if
  large preset files become common; rejected for now as more ops surface than a personal
  site warrants. Both remain viable exits if Vercel's serverless constraints ever bite.
